# Сборщик прокси (контейнер `hcg_proxy`)

Ищет рабочие прокси, проверяет их и удаляет мёртвые — сам, без вашего участия.

## Зачем

Бесплатные публичные прокси живут часы. Список, вписанный руками в `.env`,
через несколько дней превращается в список покойников: бот замолкает,
хотя код не менялся и в логах нет ошибок. Именно это мы ловили раньше.

Контейнер решает задачу целиком: находит новые адреса, проверяет каждый и
вычёркивает переставшие работать.

## Как устроено

Каждый цикл (по умолчанию раз в 10 минут):

1. **Перепроверяет то, что уже в списке.** Адрес, не ответивший три цикла
   подряд, удаляется. Не один раз — бесплатные прокси «мигают», и удаление
   после первой же неудачи вычистило бы вполне живой список.
2. **Если рабочих меньше цели** (`HARVEST_TARGET`, по умолчанию 12) —
   скачивает списки с 12 публичных источников. Когда список здоров,
   источники не трогаются вовсе: иначе нас забанят на тех самых сайтах.
3. **Проверяет кандидатов.** Не «открыт ли порт» — это ничего не значит.
   Каждый адрес получает настоящий запрос `getMe` к `api.telegram.org`.
   Ответ «401 invalid token» = успех: Telegram ответил, маршрут живой.
   Токен для проверки заведомо фальшивый (`0:HARVESTER-PROBE`), настоящий
   через чужие прокси не отправляется.
4. **Пишет результат** в общий том: `proxies.txt` (список для бота и сервера)
   и `proxies.json` (состояние со статистикой).

Бот перечитывает файл раз в 30 секунд, сервер — при отправке. Перезапуск
контейнеров не нужен.

## Как раздаются прокси

Модель — аренда, а не общий список.

Сборщик держит **резерв 15-20** проверенных адресов. Бот и сервер получают
**по 5 штук каждый**, и выданное сразу вычёркивается из резерва: сборщик
больше не проверяет эти адреса и никому их не отдаёт.

Дальше адресами распоряжается тот, кто их получил. Прокси перестал
отвечать — он **выбрасывается сразу**, без повторов и карантина, и в дело
идёт следующий из своей пятёрки. Одновременно сборщику уходит сообщение:
«вот этот мёртв, дай замену». Сборщик удаляет адрес насовсем и доливает
до пяти из резерва.

Почему выдача, а не общий список:

- два контейнера, проверяющие один бесплатный прокси, вдвое ускоряют его
  смерть и каждый узнаёт о ней отдельно;
- «уже выдан» — единственный надёжный способ не перепроверять адрес,
  который прямо сейчас в работе;
- владение делает путь отказа очевидным: выбросил своё, взял следующее,
  без обращения к сборщику и без общего состояния.

Обмен идёт через два файла на каждого потребителя в общем томе:

```
lease-bot.json       что выдал сборщик
lease-bot.ack.json   что ответил потребитель (мёртвые, сколько нужно)
lease-server.json    то же для сервера
lease-server.ack.json
```

Если контейнер упал, не успев ответить, его адреса возвращаются в резерв
и отправляются на перепроверку — иначе каждый перезапуск навсегда
откусывал бы кусок запаса.

`TELEGRAM_PROXY` нужен только до первой выдачи. Можно оставить пустым.

## Настройки

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `HARVEST_INTERVAL_MS` | `600000` | Период цикла (10 мин) |
| `HARVEST_CONCURRENCY` | `120` | Одновременных проверок |
| `HARVEST_TIMEOUT_MS` | `10000` | Предел одной проверки |
| `HARVEST_TARGET` | `12` | Сколько рабочих достаточно |
| `HARVEST_MAX` | `30` | Потолок списка |

Меньше `5000` в `HARVEST_TIMEOUT_MS` ставить не стоит — отсеет живые,
но медленные адреса.

## Что смотреть

```bash
# Лог сборщика
docker compose logs -f hcg_proxy

# Текущий список
docker compose exec hcg_proxy cat /app/data/proxies.txt

# Отчёт о последнем цикле
docker compose exec hcg_proxy cat /app/data/harvester-status.json
```

В логе каждый цикл заканчивается строкой вида:

```
Итог цикла: в списке 9 рабочих, +0 новых, −1 мёртвых, за 6 с
```

## Источники

12 штук: proxyscrape, TheSpeedX, monosans, hookzof, jetkai, roosterkid,
openproxylist, proxyspace, spys.me, geonode и два списка HTTP-прокси.

Каждый проверен вживую 5 августа 2026 года. Два популярных источника
намеренно **не** включены: `proxy-list.download` отвечает 502,
`mmpx12/proxy-list` — 404. Источник, который никогда не парсится, выглядит
точно так же, как сломанный сборщик.

Отказ одного источника — предупреждение в логе, а не остановка цикла.

## Отдельный контейнер — зачем

Проверка открывает сотни сокетов, большинство которых отваливается по
таймауту. Внутри процесса бота это подвешивало бы Telegram-polling каждый
цикл, а падение сборщика роняло бы игру. Здесь падение безвредно: бот
продолжает работать на последнем сохранённом списке.

## Локальный запуск (без Docker)

```bash
cd proxy-harvester
npm install
PROXY_DATA_DIR=/tmp/hdata npm run dev
```

## Тесты

```bash
npx vitest run proxy-harvester      # 31 тест
```

Проверка дедлайна использует настоящий сокет-«чёрную дыру», а не заглушку:
ошибка, которую она ловит, на заглушках невидима. `request.timeout` в Node
начинает действовать только после создания сокета, а при работе через SOCKS
сокет создаёт агент — прокси, который принимает TCP и замолкает, не
покрывался вообще. Замер на живом адресе: запрошено 5 секунд, реально
проверка длилась 30. Исправлено жёстким дедлайном на всю попытку.
