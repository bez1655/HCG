# Переезд HCG на новый сервер, когда бэкапа системы нет

Короткий ответ: **бэкап образа системы вам и не нужен.** Из всего, что стоит на сервере,
незаменимы четыре вещи. Остальное ставится заново командами из архива проекта.

---

## Главное: что незаменимо, а что скачивается

| Что | Незаменимо? | Почему |
|---|---|---|
| **`.env`** — пароли, токен бота, ключи | 🔴 **ДА** | Нигде больше не существует. Токен бота восстанавливается только с отзывом старого |
| **Том `hapstore-data`** — игроки, доска, журнал | 🔴 **ДА** | Живая история игры. Заново не появится |
| **Ключ Firebase** (если используется) | 🔴 **ДА** | Новый выпустить можно, но старый пропадёт безвозвратно |
| **Данные Caddy** — сертификаты + ACME-аккаунт | 🟡 Желательно | Caddy выпустит новые сам, **но только когда DNS уже смотрит на новый сервер**. А ACME-аккаунт лучше сохранить: у Let's Encrypt есть лимиты на выпуск |
| **`/etc/caddy/Caddyfile`** | 🟡 Желательно | Файл короткий, но восстанавливать проксирование WebSocket по памяти — лишняя возня |
| Исходники проекта | 🟢 Нет | Есть в `HCG-VPS.zip` у вас на компьютере |
| `node_modules`, `dist` | 🟢 Нет | Ставятся при сборке |
| Образы Docker | 🟢 Нет | Пересобираются из `docker-compose build` |
| Сам Docker, Caddy | 🟢 Нет | Ставятся одной командой. Certbot не нужен вовсе — Caddy выпускает сертификаты сам |

### Две ловушки, на которых спотыкаются чаще всего

**Первая.** Скопировать папку `/var/www/hcg` и решить, что этого достаточно.
**Данных игроков там нет.** Они в отдельном томе Docker `hapstore-data`,
смонтированном как `/app/data`. Папка проекта — это только код.
Скопируете её — получите рабочую игру с пустой доской.

**Вторая — про Caddy.** У вас стоит Caddy, а не nginx, и он хранит сертификаты
**не в `/etc/letsencrypt`**. Искать там бесполезно — этой папки просто нет.
Caddy держит их в своей папке данных, а какой именно — зависит от того, как он запущен:

| Как запущен Caddy | Где сертификаты |
|---|---|
| Служба systemd (обычная установка) | `/var/lib/caddy/.local/share/caddy/` |
| Руками от root (`caddy run`) | `/root/.local/share/caddy/` |
| В контейнере | том, смонтированный в `/data` |

**Это разные хранилища, они не связаны.** Забрать не ту папку — приехать без
сертификата. Скрипт проверяет все три по очереди и пишет, какую нашёл.

Посмотреть, как запущен ваш:
```
systemctl cat caddy | grep User=
```

## Порядок действий

### Шаг 1. Снять всё со старого сервера (PuTTY, старый сервер)

Скрипт `deploy/СНЯТЬ-СО-СТАРОГО.sh` уже в архиве проекта. Если на сервере
старая версия архива — залейте новый или создайте файл вручную.

```
cd /var/www/hcg
bash deploy/СНЯТЬ-СО-СТАРОГО.sh
```

Он соберёт в один файл `/root/HCG-ПЕРЕЕЗД-дата.tgz`:

- `.env` целиком + проверит, что ключевые поля не пустые
- том `hapstore-data` — выгружается через временный контейнер, **на остановленной игре не обязательно**, но лучше остановить: `docker compose stop hcg_app` на минуту
- `/etc/caddy/Caddyfile` — конфиг, плюс покажет, что именно проксируется
- данные Caddy — сертификаты и ACME-аккаунт, из той папки, где они реально лежат
- `caddy.service`, если юнит правили руками
- ключ Firebase, если лежит файлом
- `authorized_keys` — чтобы ваш SSH-ключ работал сразу
- слепок окружения: версии, порты, cron, файрвол, версия Caddy, содержимое Caddyfile

Скрипт печатает `✓` и `✗` по каждому пункту. **Если увидите `✗` — не переезжайте,
сначала разберитесь.** Пустой `SESSION_SECRET` или `ADMIN_PASSWORD_HASH` означает,
что новый сервер просто не стартует.

### Шаг 2. Забрать архив себе (PowerShell на Windows)

```
scp root@СТАРЫЙ-IP:/root/HCG-ПЕРЕЕЗД-*.tgz C:\Users\%USERNAME%\Desktop\
```

Не пропускайте этот шаг, даже если собираетесь копировать сервер-в-сервер.
Копия у вас на руках — единственная страховка, если старый сервер отключат внезапно.

### Шаг 3. Залить на новый сервер (PowerShell)

```
scp C:\Users\%USERNAME%\Desktop\HCG-ПЕРЕЕЗД-*.tgz root@НОВЫЙ-IP:/root/
scp C:\Users\%USERNAME%\Desktop\HCG-VPS.zip root@НОВЫЙ-IP:/root/
```

### Шаг 4. Развернуть (PuTTY, новый сервер)

```
cd /root
apt-get update && apt-get install -y unzip
mkdir -p /root/hcg-new && unzip -o HCG-VPS.zip -d /root/hcg-new
cd /root/hcg-new
bash deploy/ПОСТАВИТЬ-НА-НОВЫЙ.sh /root/HCG-ПЕРЕЕЗД-*.tgz
```

Скрипт сам поставит Docker и Caddy (из официального репозитория, не из архива
Ubuntu — там версия старая), восстановит секреты, **зальёт данные в том до первого
запуска контейнеров**, положит сертификаты туда, где их ищет именно эта установка
Caddy, выставит владельца, соберёт образы и проверит, что игроки на месте.

Почему «до первого запуска» важно: если контейнер стартует раньше, он не найдёт
состояния, создаст пустое и запишет на диск. Дальше восстанавливать придётся
поверх живой игры, с остановкой.

### Шаг 5. Переключить DNS

В панели регистратора домена `hcg.bez12.store` — A-запись на новый IP.
Обновление занимает от 5 минут до 2 часов.

Пока DNS не обновился, проверить новый сервер можно так (PowerShell, от админа):
допишите в `C:\Windows\System32\drivers\etc\hosts` строку

```
НОВЫЙ-IP  hcg.bez12.store
```

Проверили — строку удалите.

### Шаг 6. Если домен не менялся — в @BotFather ничего не трогать

Домен тот же → бот продолжит работать сам. Менять `/setdomain` и `/setmenubutton`
нужно **только если сменился адрес сайта**.

### Шаг 7. Старый сервер не удалять сутки

Оплатите ещё один период. Пока новый не отработал день без жалоб, старый —
ваш откат. Это дешевле любой ошибки.

## Что делать, если старый сервер уже недоступен

Тогда честно оцениваем потери:

| Потеряно | Можно ли восстановить |
|---|---|
| Состояние игры | ❌ Нет. Игра начнётся заново с чистой доски |
| Токен бота | ✅ Да: @BotFather → `/mybots` → @hcg1_bot → API Token → **Revoke** |
| Пароль админа | ✅ Да: `npm run hash-password -- 'новый-пароль'` → в `.env` |
| `SESSION_SECRET`, `INTERNAL_API_SECRET` | ✅ Да, генерируются заново (все разлогинятся — не страшно) |
| Сертификаты | ✅ Да, и проще, чем с nginx: Caddy выпустит их сам при первом запуске, как только DNS укажет на новый сервер. Ничего вводить не нужно |
| Ключ Firebase | ✅ Новый: Firebase Console → Настройки → Сервисные аккаунты → Создать ключ |
| Пароли игроков | ❌ Нет, но игроков можно завести заново — они получат новые |

Команды для генерации с нуля (на новом сервере, в `/var/www/hcg`):

```
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Запустите дважды — для `SESSION_SECRET` и `INTERNAL_API_SECRET`.
Всё остальное берётся из `.env.example`, там каждое поле подписано.

## Минимальный Caddyfile — если конфиг всё-таки потерялся

Восстанавливается за минуту. `/etc/caddy/Caddyfile`:

```
hcg.bez12.store {
	encode gzip
	reverse_proxy 127.0.0.1:3001
}
```

Всё. HTTPS Caddy включит сам, сертификат выпустит сам, продлевать будет сам.
WebSocket (на нём живут обновления доски) `reverse_proxy` проксирует
автоматически — в отличие от nginx, где для этого нужны отдельные строки
с `Upgrade` и `Connection`. Это как раз тот случай, когда Caddy сильно проще.

Применить:
```
caddy validate --config /etc/caddy/Caddyfile
systemctl reload caddy
```

Порт `3001` — тот, что публикует `docker-compose.yml` на `127.0.0.1`.
Наружу контейнер не смотрит, весь трафик идёт только через Caddy.

## Проверка после переезда — глазами, а не по логам

0. `systemctl status caddy` — активен; `journalctl -u caddy -n 30` — есть строка о выданном сертификате
1. Открыть `https://hcg.bez12.store` — доска рисуется, замок в адресной строке
2. Войти админом — игроки на месте, позиции фишек прежние
3. В Telegram: `/start`, потом `/help` — бот отвечает
4. Нажать «ИГРАТЬ» из бота — Mini App открывается
5. Сделать один бросок — админу приходит отчёт
6. `docker logs hcg_proxy --tail 30` — сборщик прокси нашёл адреса

Пункт 6 в Голландии, скорее всего, окажется неактуальным — и это хорошо.
Вместо ручной проверки запустите `bash deploy/БЕЗ-ПРОКСИ.sh` (см. раздел выше):
он сам проверит доступность Telegram и отключит прокси, если тот не нужен.

## Отдельно: APK

Приложение подписывается debug-ключом Capacitor, отдельного keystore в проекте нет.
Значит, переносить с сервера нечего — APK пересобирается пунктом 3 меню
`deploy/ВСЁ-НА-VPS.sh`.

Но если новый сервер получит **другой домен**, APK придётся пересобрать
обязательно: адрес сервера зашит в приложение на этапе сборки
(`VITE_API_BASE_URL` в `apk/.env`). Старый APK будет стучаться на мёртвый адрес.

## Чего в переезде НЕ нужно бояться

- **Версии Node, npm** — внутри контейнеров, версия хоста роли не играет
- **Разная ОС** — Ubuntu/Debian любой свежести подойдёт, всё в Docker
- **Ошибки при сборке образов** — не трогают данные, том отдельно; можно пересобирать сколько угодно
- **Другая архитектура (ARM вместо x86)** — образы соберутся под неё сами

## Новый сервер: 4 ядра / 4 ГБ, Голландия

Взято вместо 2 ядер / 2 ГБ в России. Что это меняет на практике.

### Мощности — с большим запасом

Замеры на реальном коде HCG (Xeon 2.6 ГГц, для порядка величин):

| Операция | Время | Смысл |
|---|---|---|
| Бросок кубика + пересчёт состояния | 0,09 мс | **11 000 ходов в секунду** на одно ядро |
| Вход игрока (PBKDF2, 100 000 итераций) | 29 мс | 34 входа в секунду на ядро |
| Запись состояния на диск | 0,03 мс | — |
| Сборка клиента | 5 с | — |

Игра не упирается в процессор и близко. 4 ядра дают запас там, где он
действительно нужен: пересборка образов при выкатке и одновременная работа
четырёх контейнеров без конкуренции за ядра.

### 4 ГБ снимают главный риск

На 2 ГБ `docker compose build --no-cache` мог упасть с `killed` — сборке клиента
через Vite нужно до 1,5 ГБ, а три контейнера уже заняли своё. Теперь этого
не случится. Swap на 2 ГБ всё равно стоит добавить — как страховку, стоит он ничего:

```
fallocate -l 2G /swapfile && chmod 600 /swapfile
mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
```

### Голландия — самое важное изменение

**Telegram там не заблокирован.** Это убирает самый капризный узел всей системы.

Напомню, чем был плох прокси: бесплатные адреса живут часами, отваливаются
в произвольный момент, и бот замолкает **без единой ошибки в журнале**.
Ровно из-за этого пришлось поднимать отдельный контейнер `hcg_proxy`
с харвестером, арендой адресов и перепроверками — примерно 700 строк кода,
существующих только ради обхода блокировки.

После переезда всё это можно выключить:

```
cd /var/www/hcg
bash deploy/БЕЗ-ПРОКСИ.sh
```

Скрипт **сначала проверяет** доступность Telegram настоящим запросом — причём
изнутри контейнера, а не с хоста (сетевые пути разные, и «с сервера curl проходит»
ещё не значит, что пройдёт у бота). Только если проверка прошла, он правит `.env`,
останавливает `hcg_proxy` и перезапускает бот. Если Telegram недоступен —
не меняет ничего и так и говорит.

Код к этому готов: при пустом `TELEGRAM_PROXY` маршрут становится
`direct connection`. Проверено вызовом `parseRoutes("")`.

Что это даёт:
- минус один контейнер и минус ~200 МБ памяти
- пропадает фоновая нагрузка: харвестер открывал 120 TLS-соединений каждые 10 минут
- **исчезает целый класс сбоев** «бот молчит, в журнале пусто»
- отклик Telegram становится стабильным вместо «как повезёт с прокси»

Откат предусмотрен: скрипт сохраняет `.env.до-отключения-прокси-ДАТА`.

### Чего ждать от смены страны

**Задержка сети.** До Голландии из России ~50–80 мс против ~10–20 мс.
Для игры-ходилки незаметно: ход не требует мгновенной реакции. А до серверов
Telegram станет наоборот ближе.

**Скорость отдачи файлов игрокам.** Видео поля — 1,4 МБ, весь бандл 620 КБ.
Из Голландии в Россию загрузится за пару секунд вместо секунды. Разница
несущественная, тем более что APK хранит ресурсы локально.

### Порты, которые нужно открыть

```
ufw allow 22/tcp    # SSH
ufw allow 80/tcp    # HTTP — нужен Caddy для выпуска сертификата
ufw allow 443/tcp   # HTTPS
ufw --force enable
```

Порт `3001` открывать **не нужно и нельзя**: контейнер слушает только
`127.0.0.1`, весь трафик идёт через Caddy. Это правильно — так и оставьте.

## Требования к серверу (для справки)

- 2 ГБ ОЗУ — минимум, со swap
- 4 ГБ — комфортно, ваш случай
- 20 ГБ диска, обязательно SSD/NVMe: состояние пишется на каждый ход
- Ubuntu 22.04 или 24.04
- Root-доступ
